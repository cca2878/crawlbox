# Storage and recovery

Authoritative history is the set of complete, pinned business snapshots. Each includes files/, artifacts/ and revision.json. Its metadata contains the parent revision, plugin identity, state, file hashes and changes. Snapshot creation uses Kopia incremental metadata checks with a stable per-source identity, disables repository actions for the upload, and rejects incomplete/error/excluded-file results. The catalog is committed only after successful snapshot creation. No-change and failed collection discard pending state.

A failure or ambiguous result during snapshot creation blocks further runs for that source until restart recovery. This avoids creating a fork when the server stored a snapshot but the acknowledgement was lost. Recovery imports complete tagged snapshots in parent order, is idempotent, and stops on a gap/fork. It never fabricates missing historical bytes. A missing or revision-mismatched current tree is restored and fully SHA-256 verified from the latest snapshot. A matching current cache is trusted without walking or hashing its contents, including after restart. Successful commits retain their candidate tree as current, avoiding a restore on the next run. Cache installation failure does not roll back a durable commit; the next run restores the snapshot.

Staging and current paths are owned by the application. Candidate construction hardlinks immutable objects on the same filesystem, with copy fallback; published objects are never modified in place. Inherited files reuse catalog digests and receive metadata checks; new/replaced files and artifacts are hashed. Kopia still walks the full candidate tree for an incremental snapshot, but no longer forces content reads for all unchanged files. Hardlink fallback copies bytes when needed. Current cache operations serialize per source, not globally. Do not edit current files externally: normal collection is not an integrity scrub and does not detect same-size out-of-band corruption. For suspected damage in the current cache, stop the manager and remove the affected current source directory; the next run restores and verifies it. If that verification fails, the mismatch is inside the snapshot rather than in the cache. Restoring cannot resolve it and every retry fails identically, so do not repeat the removal. That state has no automatic recovery: it requires deciding whether the stored bytes or the recorded digest is authoritative, and repairing the affected history accordingly. Use Kopia verification separately for repository integrity. Keep enough free disk for active downloads, restores and archives. HTTP timeouts and staging limits fail the run without advancing state. No automatic deletion of pinned history is implemented.

A revision's digests and the bytes they describe are written into the same immutable snapshot: revision.json travels inside it, so the catalog is an index over that snapshot rather than a second source of truth. Digests are computed over the candidate tree that Kopia then snapshots, with the application holding it exclusively, so the recorded digest and the stored bytes come from the same file. Recovery rebuilds catalog revisions from those snapshots, and the restore path verifies every recorded digest against the restored bytes; that round trip runs against a real Kopia repository in the integration tests, so a regression in digest computation fails before release rather than in production. Kopia cannot supply these digests itself: content-defined chunking means an object identifier addresses a list of chunks rather than the content of a file, which is also what makes deduplication work.

Inherited entries are served to plugins from those committed records. Listing a previous view or stating an inherited object returns what the catalog stored instead of rehashing the tree, which for a large view would mean reading every byte to rebuild information already held.

The management database also holds tokens, source-ID retirement records and recent runs. Back it up separately with configuration, connection credentials and TLS keys. Business snapshot recovery restores revisions and state, not old tokens or full run history. Without the management database, reissue tokens and preserve the source-ID inventory administratively; do not repurpose historical IDs. The Kopia repository itself needs independent backup.

Cache defaults to a 20 GiB soft limit; current state is outside that limit. Cache contents may be removed while the process is stopped. Staging leftovers after a crash are disposable after recovery. Configuration reload is by restart; schedules do not replay missed intervals. Default global collection concurrency is one. The timeout covers the whole run, including queue wait.

The process logs startup/error context, not Authorization headers or full token secrets. UI credentials are bcrypt hashes in an external file. Token secrets are random 256-bit values, stored as SHA-256 digests with a public lookup ID. Token scope and expiry are immutable; rotate by creating a new token and revoking the old one.

## Stopping a run and process termination

The administrator UI's run-history page offers a POST-only stop action for queued, running and validating runs. It targets the exact run ID; an old page cannot stop a newer run for the same source. Basic authentication and cross-origin protection apply. No cancellation endpoint is exposed under the public API. The UI displays a pending stop until cleanup finishes, then `interrupted`; refresh the run-history page to see the latest status. Stopping one run does not disable its cron schedule or stop another source.

Accepted cancellation closes the run context, interrupting WASM execution and HTTP work. Local hashing and copy fallback check cancellation between reads; an in-flight filesystem operation must return first. Staging is cleaned before the source is released. Timeout remains a `failed` result and includes queue wait; an administrator stop or process shutdown is `interrupted` unless a revision has already committed.

Cancellation is atomically disabled before snapshot creation starts. Requests after this boundary return HTTP 409 because a complete immutable snapshot might already exist. Snapshot or commit errors still block the source until restart recovery. Do not treat cancellation as rollback of an existing snapshot.

SIGINT/SIGTERM cancel active work and wait for cleanup. SIGKILL cannot run cleanup; on Linux, launched Kopia CLI processes are configured to die with their parent. At startup, complete snapshots are recovered before staging cleanup: a crash before a complete snapshot leaves no published revision, while a complete snapshot awaiting catalog commit is imported exactly once. Existing run records associated with recovered revisions are marked succeeded; other unfinished runs become interrupted. Ordinary standalone Linux execution uses the same behavior as containers.

## Collection preparation progress

Before the plugin starts, the authenticated UI shows revision lookup, current-cache preparation, a cache hit or Kopia restoration, restored-file verification, cache installation, and plugin startup. Restoration shows the expected total file count (including artifacts), not a downloaded count or percentage. Verification reports completed files at most once every five seconds and at completion. These host-generated updates also appear in info logs with source and run IDs; the one-minute activity heartbeat includes the current phase. Progress reporting does not scan the restore directory or add resource reads. Refresh the UI to see updates. A terminal run displays its final outcome instead of stale progress.

Plugin result messages are shown inside the run details for successful or no-change runs. The progress/result column keeps the manager's default final outcome. Empty messages do not add a detail row.

Release images are built on native amd64 and arm64 GitHub runners without QEMU. After both builds succeed, a separate job assembles the versioned multi-platform tags from the digests produced by that workflow run, for both manager and the Kopia wrapper.

The run-history UI lists 20 records per page, newest first, with previous/next links and a total count. Pagination includes records older than the most recent 100. Progress updates retain the same ordering; newly queued runs can shift page boundaries.
